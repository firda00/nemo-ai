## Шаг 1 — Создание агента (типы + детальные настройки)

### 1.1 Новые типы агентов (`AgentKind`)
Текущие: `chat`, `qualifier`, `research`, `workflow`. Добавляем:

| kind | Что делает | Поведение редактора | Бэкенд |
|------|------------|---------------------|--------|
| `manager` (Отдел/Менеджер) | Главный агент собирает команду под-агентов под сферу и управляет | вкладка Run (как workflow) + (Phase B) вкладка «Отдел» | `orchestrate` (расширить: динамические роли) |
| `coder` (Кодер) | Пишет/правит код, работает с файлами/репо | вкладка Run | новый путь поверх `orchestrate`/`research-agent` |
| `content` (Контент) | Тексты, посты, описания, креатив | вкладка Run или чат | reuse chat/run |
| `learning` (Самообучающийся) | Чат с памятью — улучшается с каждым диалогом | как chat + индикатор памяти | chat-путь + таблица памяти |

Для каждого: иконка + цвет (`platformMeta`), i18n (uz/ru/en), дефолтная модель, скелет промпта,
набор вкладок в редакторе.

### 1.2 Детальные настройки агента (новые поля, необязательные)
- `language` — уже есть.
- `country` — страна (для контекста/региональных норм).
- `purpose` — «для чего используется» (короткое назначение).
- `niche` — ниша/сфера (напр. образование, e-commerce, недвижимость…). Влияет на промпт и на роли в отделе.

**Данные:** `agents` + колонки `country text`, `purpose text`, `niche text` (nullable).
**Типы:** `PlatformAgent` += `country?/purpose?/niche?`.
**UI:** новый блок в онбординге (шаг 1) и в редакторе (вкладка General), сворачиваемый «Доп. настройки».

### 1.3 Отдел / Менеджер — Phase A (сейчас): команда на лету
- Расширить `orchestrate`: менеджер выбирает роли **динамически** под `niche`/`purpose`, а не фиксированные
  4. Промпт менеджера учитывает нишу/страну/язык агента.
- UI: `OrchestratorRunner` уже показывает живую работу команды — переиспользуем.

### 1.3b Отдел — Phase B (позже): постоянные отделы
- Таблицы `departments` (id, account_id, main_agent_id, name, niche) и `sub_agents`
  (id, department_id, role, prompt, model). Главный агент создаёт под-агентов под сферу → они сохраняются и
  управляются как отдел. Отдельная вкладка/страница «Отдел».

### 1.4 Кодер и Контент-агенты
- `coder`: runner; код-ориентированный system prompt; вывод — Markdown с блоками кода/диффами.
- `content`: генерация контента; маркетинговый system prompt; вывод — Markdown.
- Оба на бесплатных моделях OpenRouter (текст/код — ок; веб-поиск недоступен на free).

### 1.5 Самообучающийся агент (память)
- Таблица `agent_memory` (id, agent_id, account_id, summary text, created_at).
- Chat-путь (`test-agent`, `telegram-webhook`): перед ответом подмешиваем последние N summary в system prompt;
  после диалога — суммируем и сохраняем. MVP: хранить последние сводки и подмешивать.

## Шаг 2 — Интеграции (каталог по регионам)
- Переделать `IntegrationsPage` в **каталог с поиском + фильтрами** по категории и стране.
- Данные: файл-каталог, группировка по категориям (мессенджеры, CRM, телефония, маркетплейсы, платёжки,
  календари, helpdesk, e-commerce) и тегам регионов (UZ, RU, US, EU, MENA, Africa, Global).
- Большинство — карточки «Запросить / Скоро» на старте; реальное подключение для поддерживаемых
  (Telegram — живой). Метод подключения per-integration (token/oauth/webhook).
- Бэкенд: уже есть общий `connect-channel`; расширяем постепенно.

## Шаг 4 — Токены / биллинг (обсуждаем отдельно, последним)
- Пул Nemo-токенов из нашего OpenRouter-кошелька (стартовые $5–10). Расход списывает баланс (уже есть
  `token_balance` + `usage` + RPC `decrement_token_balance`). Баланс = 0 → предложить вставить свой ключ.
- Админ выдаёт токены/гифт-карты (уже есть `admin-api` + `redeem-gift`).
- В основном это UX + связывание; финализируем после шагов 1–3.

## Заметки по ограничениям
- Бесплатные модели OpenRouter не умеют веб-поиск (Sonar платный) и иногда лимитируются (есть retry).
- Все ключи — только на сервере (edge functions). Фронт никогда не видит секреты.
- Секреты, засвеченные в чате ранее, нужно ротировать.
