# Первая админка платформы

Короткий документ про один шаг установки, у которого раньше не было шага: как получить права
администратора платформы на свежей базе.

## Что было и почему изменилось

До миграции `20260822090000_bootstrap_admin_without_hardcoded_email` права выдавались триггером
регистрации: он сравнивал почту нового пользователя с адресом, зашитым прямо в схему, и при
совпадении ставил `is_admin = true`.

Три беды в одной строке:

1. **Личный адрес уезжал в каждую копию платформы.** Nemo разворачивают у себя — чужая почта в
   чужой базе не нужна никому.
2. **Сравнение шло по неподтверждённой почте.** На установке с выключенной проверкой писем
   достаточно было зарегистрироваться под этим адресом, чтобы стать администратором.
3. **Права выдавались молча, внутри триггера.** По журналу видно регистрацию — не то, что вместе с
   ней выданы права на всю платформу.

Теперь регистрация **никогда** не выдаёт прав: `is_admin = false` для всех без исключения. Первая
админка — отдельная, ручная, привилегированная операция.

## Как выдать первую админку

**1. Зарегистрируйтесь через обычный интерфейс и подтвердите почту.**

Подтверждение обязательно: неподтверждённый адрес — это заявка, а не доказательство.

**2. Узнайте идентификатор пользователя.**

```sql
select id, email from auth.users order by created_at desc limit 5;
```

**3. Выполните выдачу от роли, которой прогонялись миграции** (в Supabase это `postgres` —
SQL-редактор в панели проекта или `psql` со строкой подключения владельца):

```sql
select * from public.claim_platform_admin('00000000-0000-0000-0000-000000000000');
```

Ответ — одна строка: `user_id`, `email`, `granted`, `note`.

| `note` | что это значит |
| --- | --- |
| `выдано` | готово, права есть |
| `почта не подтверждена` | вернитесь к шагу 1 |
| `пользователя нет` | неверный идентификатор, либо пользователь ещё не попал в `public.users` |
| `администратор уже есть — назначайте через существующего администратора` | функция отработала раньше |

## Почему функция работает только один раз

Пока администраторов нет, `claim_platform_admin` выдаёт права. Как только появился первый —
перестаёт навсегда. Дальше администраторов назначает администратор, через админ-панель.

Иначе «процедура начальной установки» осталась бы вечно открытой дверью, о которой через полгода
никто не помнит.

## Кто может её вызвать

Только владелец функции (роль, от имени которой прогонялись миграции) и суперпользователь. С
`public`, `anon`, `authenticated` и `service_role` права сняты явно.

`service_role` — тоже нет, и это не перестраховка: этим ключом ходят Edge Functions, то есть код,
который правится чаще, чем пересматриваются права.

## Что проверяется автоматически

`agent-hub/auth-rls-contracts.mjs`, раздел E. Контракты воспроизводят **все** миграции по порядку и
проверяют конечное состояние, а не текст последнего файла:

- регистрация не выдаёт админку по совпадению почты;
- `claim_platform_admin` существует, требует подтверждённой почты, берёт замок перед подсчётом и
  работает только пока администраторов нет;
- право на вызов не осталось ни у одной прикладной роли — с учётом всех `grant`/`revoke`/`drop` из
  истории, а не только последнего файла;
- `deploy/init-supabase.sql` собран из текущих миграций и не содержит личных адресов.

## Личные адреса в раздаваемой схеме

`deploy/init-supabase.sql` собирается из миграций генератором `deploy/build-init-sql.mjs`. Уже
применённые миграции не переписываются — на боевой базе они отработали, и правка сделала бы историю
расходящейся с фактом. Вместо этого генератор заменяет известные личные адреса на
`redacted@invalid` (домен из RFC 2606, который не может существовать) и печатает число замен и
файлы — без самих адресов, потому что журнал сборки тоже хранится.

Незнакомый адрес в миграции **останавливает сборку**. Решение принимает человек: личные данные —
внести литерал в `REDACTABLE`; адрес нужен по делу — оставить и добавить исключение осознанно.
